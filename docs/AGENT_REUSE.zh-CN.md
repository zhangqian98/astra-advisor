# 子代理上下文复用

本版把“选择模型”和“新建还是复用 worker”分开：**先确定能力下限，再决定复用**。
同任务返工优先继续使用已经理解代码的 worker，发送问题、代码变化和验收条件，
而不是每轮重新启动一个 agent、重新贴全量上下文。不是所有任务都应该复用。

## 什么时候复用

需要当前原生工具确认同一个 agent、模型和 reasoning effort，且仍处于同一父会话、
工作区、运行时版本和任务边界。已有完成记录、上下文可信、增量任务准备好时，优先
继续原 worker。同模块小追加任务需要明确选择 `related_task`；不默认跨任务复用。

上下文过时、出现错误假设、模型需要升级、连续失败、接近上下文上限，都会改用新
worker。agent 正在工作时返回 `wait`，不能借此又派一份重复工作。

默认最多连续复用四轮、距离上次完成不超过六小时；可观察的上下文用量达到上限的
75% 时新建。派发决策五分钟后失效。这些是初始保守策略，不是缓存有效期或经过
实测校准的最优值。无 token 遥测时保留 unknown，不伪造计数。

**最终 reviewer 永远是新的独立只读上下文。** reviewer 的发现可以返回原实现者修复，
之后父线程重新验证，并启动另一个全新的 reviewer。

## 实际执行顺序

```text
routing_memory.py plan   选择模型和强度
        ↓
agent_reuse.py plan      决定 fresh / reuse / wait / blocked
        ↓
agent_reuse.py claim     原子预约 worker 和写入文件
        ↓
Astra 调用当前真正可用的原生 spawn / follow-up / resume 工具
        ↓
routing_memory.py feedback
        ↓
agent_reuse.py finish    记录实际复用状态和用量，释放预约
        ↓
发现旧上下文错误：agent_reuse.py lesson
        ↓
父线程验证 → 全新独立审查 → agent_reuse.py gate
```

这是 Skill 要求 Astra 执行的流程，不是自动拦截原生工具的 hook；没有实际执行就
不能声称复用策略已经生效。原生接口不支持继续会话时，新建合适 worker 或保留安全的
父线程工作，不伪造工具。`fork_turns: none` 约束的是新建，不意味着每次跟进都必须重建。

预约会阻止两个调用者同时占用一个 worker 或修改相同文件。超时不会自动释放尚未
结束的任务；必须确认 worker 已停止，记录取消或失败证据后再完成预约。新反馈、源码
变化和过期证据会让未执行的决策失效，要求重新路由。

## 如何从失败中改进

普通反馈继续区分模型能力不足、规格不清、环境故障等原因。确认是旧上下文导致
问题时，再记录 `stale_context`、`anchoring` 或 `context_overflow` 类型的经验。
后续相同任务类别、模型和运行时会更谨慎地复用，必要时直接新建。

一次确认的上下文问题触发七天谨慎期。三个独立任务的失败达到衰减样本条件后可以
持续影响策略；三十天半衰期，九十天过期。同一任务重试不冒充多个独立样本。
后来才发现的错误同样能够记录；错误归因可通过已有 `void` 操作撤销，保留审计记录。
这改变的是路由和复用策略，不是训练模型权重。

## 费用与隐私

复用可能减少重复搜索和上下文重建，但**保留上下文不等于历史输入免费，也不保证
缓存命中或净省钱**。报告分别展示 fresh/reuse 的观测调用、失败、input、cached input、
output 和延迟，未知值保留 null，不把不同任务组的平均差直接写成节省率。
费用回执仍由原有计算器处理，不重复加总缓存 token 或累计会话用量。

数据库、会话记录和证据保存在当前工作仓库的 Git 元数据目录内。不同 worktree 共享
学习历史，但不自动共享活跃 worker；不会自动上传私有历史、代码、任务文本或个人信息。
源码中没有为某个用户硬编码账户信息。GitHub 自己生成的提交账户/noreply 元数据与
源码隐私是不同的层面。
